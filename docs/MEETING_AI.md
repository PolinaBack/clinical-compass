# Локальная расшифровка встреч и черновики итогов

Разрешённая часть E15: AI-01…AI-06, AI-08 и необходимые согласия/хранение записи. Пользователь выбрал **локальную обработку на компьютере с PyCharm** и **черновик итогов/следующих шагов по разговору, который проверяет врач**. Извлечение историй болезни AI-07, автоматическое разделение голосов и полный видеосервис E14 остаются отдельными открытыми задачами. E03 отложен; все 806 требований сохраняются.

## Что уже делает программа

Врач открывает «Календарь» → пациента → встречу. Сначала показан свёрнутый список «Запись 1», «Запись 2» и далее. Выберите запись, чтобы открыть обработку, расшифровку и итоги. В расшифровке доступны поиск по фразе и переход между совпадениями; повторяющиеся пункты/предложения итогов не дублируются. JSON-скачивание удалено. [Подробности](MEETING_REFINEMENTS.md).

**Один раз у пациента:** откройте «Настройки → Записи встреч», включите нужные пункты и нажмите «Сохранить разрешения записей». Четыре пункта независимы: аудио, видео со звуком, расшифровка, итоги. Выбор действует для своих встреч до изменения; изначально всё выключено. Старые предпочтения и согласия одной встречи не переносятся автоматически — новые разрешения нужно сохранить один раз. У врача собственных форм согласия нет.

**Загрузка у врача:** «Мои пациенты» → пациент → «Консультации и видео» → «Записи встреч, расшифровки и проверенные итоги» → «Подготовить расшифровку встречи» или «Открыть запись и итоги». Если встреч нет, добавьте приём. В блоке «Загрузить запись» выберите вид, файл MP4/WebM или аудиофайл и кнопку «Загрузить запись». Пределы — 200 МБ, два часа, обязательно звук. Повторно ждать подтверждения этой встречи не нужно; сервер проверяет текущие настройки пациента. Для первого теста удобен фрагмент **2–5 минут**. Длинное видео также принимается и обрабатывается частями.

Пациент не может загружать и воспроизводить аудио/видеофайлы. Плеер и полная расшифровка доступны только ведущему врачу; прямой URL файла, в том числе запрос части файла, возвращает пациенту 403. В пациентском интерфейсе нет полного текста расшифровки. JSON-выгрузка больше недоступна ни одной роли. Согласия/отзыв и существующее удаление сохраняются; из результатов пациент получает только включённые врачом пункты отдельно опубликованных итогов. До публикации черновик не виден. Для проверки обеих ролей используйте разные окна браузера, одно из них приватное.

1. Назначьте приём в существующей форме консультаций. Для записи уже состоявшегося разговора можно создать приём с его датой. В списке встреч нажмите «Подготовить расшифровку встречи».
2. У пациента один раз сохраните нужные разрешения в настройках: для аудио — аудиозаписи и расшифровка, для видео — видеозаписи и расшифровка, для итогов дополнительно итоги. Настройки врача и формы разрешений каждой встречи отсутствуют.
3. Врач сам загружает и запускает обработку файла. Разрешение не включает камеру, микрофон и автоматическую запись звонка. Если пациент выключит нужный пункт, новая загрузка/обработка запрещается, ожидающие и выполняемые подходящие задачи отменяются; поздний результат не сохраняется. Прежние данные не удаляются автоматически.
4. Нажмите «Расшифровать запись». Задача сохранится в SQLite. Отдельный обработчик распознает речь и сохранит машинную версию с таймкодами. Обновите страницу, чтобы увидеть результат.
5. Сверьте слова и названия лекарств с оригиналом. Говорящие сначала обозначены «не определён»: модель не угадывает, кто врач и кто пациент. Исправьте текст/подписи и сохраните новую версию.
6. Нажмите «Подготовить итоги и следующие шаги». Ollama локально выделит главное из всех частей и подготовит один краткий итог всей встречи. На экране появятся до трёх абзацев о контексте, жалобах/важных темах и итогах, до трёх следующих шагов и до одного вопроса для врача; всего до 220 слов. Пустые разделы не выводятся. Повторы объединяются, конец встречи не отбрасывается. Говорящих, ответственных, сроки и жалобы, которых нет в разговоре, модель не должна угадывать.
7. Откройте «Редактировать, проверить источники и опубликовать». Проверьте каждый оставленный пункт, исправьте формулировки, снимите отметки у ненужных. Исходные цитаты и переходы к записи раскрываются отдельно у каждого пункта. Ссылки на фрагменты помогают проверке, но не доказывают правильность вывода модели. Перед публикацией обязательны отметки о сверке смысла и всех названий лекарств/доз по записи.
8. Только «Подтвердить итоги и показать пациенту» открывает выбранные итоги и следующие шаги пациенту. Вопросы/фидбек для врача остаются в его кабинете. Можно снять публикацию. Изменение расшифровки требует новой сводки и проверки.

Расшифровки, версии правок, сводки и подтверждения хранятся отдельно. История открывает прежние тексты. Нет действий автоматического назначения/отмены лечения, выставления диагноза, изменения дневника, шкал или схемы лекарств. Кнопки таймкодов перемещают плеер к оригиналу; без JavaScript доступны обычные элементы плеера.

## Обновить проект в PyCharm

Остановите старый сервер: Stop или Ctrl+C. Сохраните собственные незакоммиченные изменения через Commit/Shelve Changes. В Terminal из корня `clinical-compass`:

```powershell
git fetch origin
git switch feat/local-mvp
git pull --ff-only origin feat/local-mvp
.\.venv\Scripts\python.exe -m scripts.backup data/backups/before-meetings.db
.\.venv\Scripts\python.exe -m pip install -r requirements-meetings.txt
```

Для копии базы используйте новое имя. При расхождении истории Git не применяйте reset/force; сохраните текст сообщения. Существующую SQLite и аккаунты не пересоздавайте. В macOS/Linux замените `.\.venv\Scripts\python.exe` на `.venv/bin/python`.

## Один раз установить модели на своём компьютере

Нужны свободное место для моделей, 64-битный Python 3.11+ и память для локального распознавания/модели на 3 млрд параметров. Начальная конфигурация: Faster Whisper small, CPU/int8, и `qwen2.5:3b` в Ollama. Скорость зависит от компьютера; CPU может обрабатывать встречу дольше самой записи.

1. Установите [FFmpeg](https://ffmpeg.org/download.html) и [Ollama](https://ollama.com/download). В Windows можно использовать:

   ```powershell
   winget install --id Gyan.FFmpeg -e
   winget install --id Ollama.Ollama -e
   ```

   Затем откройте новый Terminal, чтобы обновился PATH. Проверка: `ffmpeg -version`, `ffprobe -version`, `ollama --version`.
2. Запустите Ollama без облачных моделей. Если приложение Ollama уже работает в трее, завершите его через меню значка. В отдельном Terminal:

   ```powershell
   $env:OLLAMA_NO_CLOUD="1"
   ollama serve
   ```

   Этот Terminal оставьте открытым. В macOS/Linux: `OLLAMA_NO_CLOUD=1 ollama serve`. Другой экземпляр не должен занимать порт 11434.
3. В другом Terminal PyCharm скачайте модели. Это единственный этап, которому нужен интернет; записи пациентов в нём не читаются и не отправляются:

   ```powershell
   .\.venv\Scripts\python.exe -m scripts.setup_meeting_ai --download-whisper --pull-summary
   .\.venv\Scripts\python.exe -m scripts.setup_meeting_ai
   ```

   Скачиваются веса из `Systran/faster-whisper-small` и локальная `qwen2.5:3b`. Для Whisper фиксируются commit источника и SHA-256 весов; перед распознаванием сумма проверяется повторно. Во время обычной обработки модели автоматически не скачиваются. Повреждённые веса не используются.
4. Диагностика должна показать «готово» для FFmpeg, пакета, файлов модели и Ollama. Наличие компонентов ещё не подтверждает медицинскую точность распознавания.

Облачная среда разработки вернула `403` при обращении к Hugging Face; весов Whisper здесь нет, Ollama с моделью не запущена. Поэтому **настоящий прогон моделей в облаке не подтверждён**. Проверки программы используют явно синтетические результаты в отдельных тестовых БД. Чтобы распознавание заработало у вас, выполните установку выше на компьютере с доступом к источникам моделей. Нельзя считать синтетические тесты проверкой качества ИИ на реальной встрече.

## Запуск приложения и очереди

После настройки нужны три работающих процесса: Ollama, приложение и обработчик. Ollama уже запущена выше.

В Terminal приложения:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Сначала дождитесь сообщения `Application startup complete`: миграции 005–007 добавят таблицы встреч, прогресс и разрешения аккаунта пациента, сохранив прежние события. Для нового порядка пациент один раз сохраняет разрешения в настройках; у врача ничего подтверждать не нужно.

Во втором Terminal:

```powershell
.\.venv\Scripts\python.exe -m scripts.meeting_worker
```

Обработчик читает ту же SQLite (`COMPASS_DB`, если задан, должен совпадать у обоих процессов). Не нужно запускать его заново для каждой записи. Для обработки максимум одной задачи есть `--once`.

Откройте `http://127.0.0.1:8000`, войдите врачом. Для отдельного входа пациента используйте другое или приватное окно браузера. По умолчанию интерфейс и Ollama доступны только на этом компьютере.

«Ожидает обработчика» означает, что задача сохранена, но её ещё не забрал worker. «Выполняется» — обработчик взял задачу; продвижение проверяйте по индикаторам ниже. При ошибке есть понятная причина. После исправления нажмите соответствующую кнопку снова; повтор не создаёт дубликат результата. При аварии процесса задача после истечения аренды (10 минут без контрольной точки) отмечается как прерванная; повтор требует явного действия врача.

### Как видеть продвижение и возможную остановку

В карточке задачи у врача теперь есть:

- **Этап:** извлечение звука, проверка/загрузка модели, поиск речи, распознавание, проверка и сохранение результата.
- **Распознано до 12:30 из 43:26:** время по настоящим таймкодам полученных фрагментов. Процент не растёт от одного ожидания. До завершения сохранения максимум 99%; 100% означает сохранённый результат. Во время подготовки точный процент неизвестен, вместо него показан неопределённый индикатор. Для итогов считаются реально завершённые части разговора.
- **«Обработчик на связи»** и возраст последнего сигнала. Сигнал приходит примерно раз в 5 секунд даже во время загрузки модели и длительного нативного вызова. Это подтверждает связь с процессом, но не доказывает продвижение модели.
- **Предупреждения:** нет сигнала более 30 секунд либо прогресс не менялся более двух минут. Они помогают проверить Terminal, но не объявляют программу зависшей: длинная подготовка и отдельные фрагменты тоже занимают время.

Страница сама запрашивает только метаданные раз в 5 секунд, пока вкладка видима. Текст, плеер и формы не перезагружаются; несохранённые правки остаются на месте. После завершения нажмите «Показать расшифровку» / «Показать итоги», чтобы открыть сохранённый текст. При потере связи явно показано, что данные устарели. Без JavaScript обновляйте страницу вручную, предварительно сохранив правки. Пациент не получает API, прогресс и тексты обработки.

В Terminal обработчика также появляются время, номер задачи, этап и обработанные секунды — без слов разговора и имени файла. Эти сообщения выводит именно обновлённый `scripts.meeting_worker`.

**Как включить после обновления:** уже работающую старую задачу можно оставить до завершения — получить от неё новые сигналы без перезапуска нельзя. Затем обновите `feat/local-mvp`, перезапустите основное приложение, дождитесь `Application startup complete` (применятся миграции 006/007), и запустите обработчик заново. Записи, итоги и история разрешений сохраняются. Worker проверяет наличие 007 до запуска. Пациент один раз сохраняет новые разрешения аккаунта в настройках. Для старой задачи без метаданных страница прямо показывает отсутствие данных об активности.

Для текущего запуска старой версии можно открыть Windows **Диспетчер задач → Подробности** через Ctrl+Shift+Esc и смотреть процесс Python, которому соответствует обработчик, его загрузку CPU и накопленное время CPU. Это косвенные признаки работы, а не доказательство, что распознавание продвигается. Не завершайте процесс только из-за краткой паузы показателей.

### Если появилось `no such table: meeting_recordings`

Это означает, что в базе, которую открыл обработчик, ещё нет таблиц встреч. Они добавляются миграцией 005 при запуске **обновлённого основного приложения**. Возможны две причины: приложение после обновления ещё не перезапускалось либо приложение и обработчик открывают разные базы.

1. В PyCharm остановите старое приложение кнопкой Stop или Ctrl+C. Из корня проекта запустите команду `uvicorn` выше и дождитесь `Application startup complete`. Этот Terminal оставьте открытым.
2. В другом Terminal из того же проекта снова выполните команду `scripts.meeting_worker` выше.
3. Если таблиц всё ещё нет, проверьте путь к базе в обоих окружениях:

   ```powershell
   .\.venv\Scripts\python.exe -c "from app.storage import default_path; print(default_path().resolve())"
   ```

   Обычно это `C:\Users\balin\PycharmProjects\clinical-compass\data\compass.db`. Если приложение запускается через Run Configuration PyCharm, проверьте там **Environment variables → COMPASS_DB** и **Working directory**: настройки Run Configuration не переносятся автоматически в Terminal. Оба процесса должны открывать вашу существующую базу. Не меняйте путь на случайный файл и не удаляйте старую SQLite.

В исправленной версии обработчик сначала проверяет существующий файл в режиме чтения. При отсутствии базы или миграции он показывает её полный путь и эти инструкции, завершаясь без длинной трассировки. Он не создаёт пустую базу и не применяет миграции самостоятельно. Установка моделей Whisper/Ollama — отдельный шаг; она не создаёт таблицы SQLite.

### Если расшифровка завершилась с сообщением «Обработка не завершилась»

Это общий статус ошибки, а не подтверждение конкретной причины. Старые версии сохраняли только `processing_failed`, поэтому по экрану и сообщению о запуске обработчика установить техническую причину нельзя.

После получения обновлений откройте **новую вкладку Terminal** в PyCharm, из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m scripts.setup_meeting_ai --check-transcription
```

Это другая команда, чем `scripts.meeting_worker`. Она сама создаёт одну секунду тишины, проверяет FFmpeg, контрольную сумму и настоящий запуск локальной модели, включая механизм выделения речи. Она не открывает базу и записи встреч, не скачивает модели и не обращается к Ollama. Текст, если модель вернула его на тишине, не выводится. Проверка может занять некоторое время на загрузку модели; запускайте её, когда обработчик не обрабатывает встречу, чтобы не держать две копии модели в памяти.

При ошибке показаны этап и техническая причина. Здесь исходный звук заведомо искусственный, поэтому можно показать исключение среды, не раскрывая разговор. Пришлите этот вывод для разбора. Успешный короткий тест не доказывает качество распознавания речи и способность обработать 43-минутную запись в доступной памяти.

Исправлен пропуск загрузчика: словарь модели бывает `vocabulary.json` или `vocabulary.txt`, как учитывает загрузчик самого Faster Whisper. Теперь загружаются оба поддерживаемых варианта, а отсутствие любого словаря означает неполную установку. Если диагностика сообщает, что модель отсутствует или загружена не полностью, дополните её явной командой, которой нужен интернет:

```powershell
.\.venv\Scripts\python.exe -m scripts.setup_meeting_ai --download-whisper
```

Затем повторите `--check-transcription`. Общая команда установки также проверяет Ollama; эта часть относится к подготовке итогов, а отдельная проверка `--check-transcription` проверяет именно распознавание. После устранения причины перезапустите обработчик через Ctrl+C и `scripts.meeting_worker`, обновлённое приложение и нажмите «Расшифровать запись» у уже загруженного файла. Перезагрузка видео и пересоздание SQLite не нужны.

При следующем неизвестном сбое обработчик дополнительно выведет только номер задачи, этап и тип исключения, без текста исключения, расшифровки, имени файла и содержимого записи. Например: `stage=transcribe exception_type=RuntimeError`. Это помогает связать сбой с распознаванием, но само по себе не объясняет причину RuntimeError. При повторной обработке записи согласия и ограничения доступа остаются прежними.

### Если появилась ошибка `open() got an unexpected keyword argument 'metadata_errors'`

Это подтверждённая несовместимость Faster Whisper 1.1.1 с PyAV 19: модель передаёт параметр, удалённый из новой версии декодера. Ошибка воспроизведена на искусственном WAV без весов модели. В `requirements-meetings.txt` закреплена проверенная **PyAV 18.1.0**, с которой настоящий декодер Faster Whisper успешно читает звук. Модель и видео заново скачивать не требуется.

### Если Ollama работает, а приложение сообщает об ошибке итогов

Работающие `/api/show` и обычный `/api/chat` ещё не подтверждают выполнение именно запроса приложения: он использует `stream=false`, строгую JSON-схему в `format`, `num_ctx=8192`, `num_predict=1000` для опорных заметок и `2400` для финального итога, системную инструкцию, части расшифровки и проверку цитат. В старой версии HTTP-ошибка, неверный JSON и некоторые ошибки оболочки ответа имели одно сообщение «Ollama недоступна». По нему нельзя восстановить конкретную причину задним числом.

`invalid_summary`, этап `validate_summary`, HTTP 200 означает: Ollama ответила и её текст удалось разобрать как JSON, но структура, цитата или ссылка на фрагмент не прошла проверку. Это не ошибка подключения. В прежнем сообщении точное нарушенное правило не сохранялось.

По уточнению пользователя «можно чтобы она не была супер точной» итоги пишутся **своими словами**. Модель возвращает краткий пересказ и номер выбранного источника (`text`, `source_id`); переписывать цитаты ей больше не нужно. Программа заранее готовит исходные отрывки из расшифровки и сама подставляет выбранный текст, ID сегмента и переход к оригиналу. Длинный сегмент делится без потери конца, короткая реплика показывается с соседним контекстом. Существующие версии, правки и формат сохранённых сводок сохраняются.

[Структурированный ответ Ollama](https://github.com/ollama/ollama/blob/main/docs/api.md#chat-request-structured-outputs) задаёт три обязательных раздела и допустимые источники именно текущей части. Если JSON/структура/номер источника неверны, в рамках задачи допускается **одна** новая генерация на тех же источниках с указанием нарушенного правила. После второго отказа ничего не сохраняется. Ошибки сети/HTTP/протокола и усечение ответа не запускают такой повтор. До и после каждого вызова снова проверяются действующие согласия и доступ. Пустое вступление не прерывает обработку последующих частей. Если итогов нет ни в одной части, программа сообщает об этом, сохраняя исходную расшифровку.

Подставленный отрывок подтверждает происхождение текста, но сам по себе не доказывает правильность пересказа. Врач проверяет смысл и лекарства перед публикацией; автоматические назначения и отмены лечения не выполняются. Пациент не получает оригинал, полную расшифровку и машинные черновики.

После получения обновлений откройте **новую вкладку Terminal PyCharm** из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m scripts.setup_meeting_ai --check-summary
```

Команда показывает фактический адрес/модель и проверяет **тот же запрос приложения** на фиксированном искусственном разговоре. Whisper, модель речи, база, встречи и медицинские записи ей не нужны; модели она не скачивает. Она возвращает код 0 при успехе и 1 при сбое. Если Ollama ответит ошибкой HTTP, в этой проверке можно показать её текст: вход заведомо искусственный. Текст успешной сводки не выводится, данные не сохраняются. Совмещать флаг с другой проверкой или скачиванием запрещено.

Новые причины различаются:

| Код | Что означает |
|---|---|
| `summary_provider_unavailable` | Не получено соединение/ответ от локального сервиса; проверьте адрес и окружение именно обработчика |
| `summary_timeout` | Истёк лимит чтения ответа на часть: по умолчанию 900 с; можно уменьшить часть или настроить ожидание |
| `summary_configuration_invalid` | Неверные пределы ожидания/разбиения либо разные настройки приложения и worker |
| `summary_model_missing` | HTTP 404: проверьте модель и адрес; успешная ручная проверка другого имени/порта не проверяет эту конфигурацию |
| `summary_request_rejected` | HTTP 400/422: сервер отклонил параметры |
| `summary_provider_http_error` | Другая ошибка HTTP, например 500; причину покажут искусственная проверка или журнал Ollama |
| `summary_protocol_invalid` | Ответ получен, но HTTP/JSON-оболочка не соответствует протоколу Ollama |
| `summary_json_invalid` | HTTP 200, но текст итогов не является правильным JSON |
| `summary_output_truncated` | Генерация не завершена или `done_reason=length`; частичный ответ не сохраняется |
| `invalid_summary` / `empty_summary` | JSON получен, но нарушены структура/цитаты/номера фрагментов либо нет подтверждённых пунктов |

При `invalid_summary` проверка дополнительно выводит `Правило: …`: `groups` — три раздела; `category_items` — списки; `model_item_fields` — поля ответа `text/source_id`; `source_id` — номер источника из текущей части. Для уже сохранённых/отредактированных сводок сохраняются проверки `item_fields`, `text`/`quote`, `segment_ids`, `quote_not_found`. Ответ модели и разговор в этот вывод не попадают.

В **рабочей задаче** сохраняется только код; журнал выводит этап, HTTP-код и `validation=…` из фиксированного списка правил, без тела ответа и цитат. Для разбора пришлите вывод `--check-summary`. Если короткая проверка прошла, это ещё не проверка всех частей длинной расшифровки; при повторной ошибке нужна строка из Terminal **обработчика** с `code=… stage=… HTTP=… validation=…`. Код 303 в журнале Uvicorn означает приём запроса/перенаправление, а не успешный ответ модели. Запросы самого Ollama видны в его журнале, не в окне Uvicorn.

Чтобы получить исправление, остановите обработчик (Ctrl+C), обновите существующую ветку и запустите искусственную проверку:

```powershell
git switch feat/local-mvp
git pull --ff-only origin feat/local-mvp
.\.venv\Scripts\python.exe -m scripts.setup_meeting_ai --check-summary
```

После успешной проверки перезапустите приложение и обработчик по командам выше. В браузере откройте **Кабинет врача → пациент → Консультации и видеосвязь → Записи встреч**, нужную встречу и повторите подготовку итогов. Уже загруженное видео и готовую расшифровку сохраняйте: повторная загрузка и новое распознавание не требуются. Зависимости Python и модель в этом исправлении не менялись.

После обновления для новых кодов ошибок нужно перезапустить обработчик. Существующий файл и расшифровку повторно загружать не нужно. Переход на другую модель, изменение контекста или памяти не выполняются по предположению: сначала нужен точный код/ответ проверки. Итоги остаются черновиком до проверки врача, пациент не получает ошибки обработки и машинные результаты.

### Если первая часть готова, а следующая завершилась `summary_timeout`

Это ограничение ожидания отдельного ответа. В версии с лимитом 180 секунд журнал мог показать готовую первую часть, затем ровно через три минуты — ошибку следующей. По одному такому сообщению нельзя установить загрузку памяти/процессора или причину задержки модели.

Теперь чтение ответа `/api/chat` по умолчанию допускает **900 секунд (15 минут)**, а порог разбиения уменьшен с 6000 до **3000 символов с учётом служебного запаса**. Источники не выбрасываются: частей может стать больше. `/api/show` сохраняет короткий лимит 10 секунд, подключение — 5 секунд. Heartbeat продолжает показывать связь; процент растёт только после проверенной части. Бесконечного ожидания и автоматического повторения запросов после тайм-аута нет.

Для первой проверки удобно загрузить запись на **2–5 минут**. Большой файл вручную делить необязательно. Повтор подготовки итогов использует готовую расшифровку, но готовит итог заново; сохранение промежуточных частей для продолжения после сбоя пока не реализовано. Настоящая скорость модели на вашем ПК проверяется отдельно.

Дополнительная настройка обычно не нужна. Если требуется, в **обоих** терминалах приложения и обработчика перед запуском задайте одинаковые значения:

```powershell
$env:COMPASS_SUMMARY_TIMEOUT_SECONDS = "1800"
$env:COMPASS_SUMMARY_CHUNK_CHARS = "1500"
```

Допустимы 60–3600 секунд и 1500–6000 символов соответственно. Затем заново запустите приложение и worker. Эти параметры входят в отпечаток задачи: менять их только у worker недостаточно, такую задачу приложение отменит как изменённую конфигурацию. Проверка `python -m scripts.setup_meeting_ai --check-summary` показывает фактически используемые значения. Для возврата к значениям по умолчанию удалите обе переменные окружения в обоих терминалах и перезапустите процессы.

## Хранение, отзыв и права

- Аудио/видео проверяются FFprobe по фактическому содержимому: нужен звук, до 200 МБ и двух часов. Форматы WAV, MP3, FLAC, OGG, M4A, MP4, WebM. Произвольные интернет-ссылки не загружаются.
- Разрешения проверяются при загрузке, постановке в очередь, перед обработкой, между сегментами/запросами и перед сохранением. Даже отзыв с последующим повторным согласием не разрешает завершить старую задачу. Изменение состава, доступа, исходного текста или модели требует новой проверки.
- Во время одного локального вызова модели мгновенная остановка не обещается. После изменения согласий результат отбрасывается и следующие шаги не запускаются. Ни один запрос к внешнему ИИ API не предусмотрен; Ollama допускается только по loopback HTTP, перенаправления и облачные модели отклоняются.
- Новые записи и тексты доступны 30 дней после загрузки. По истечении срока доступ и обработка запрещены; работающий worker очищает содержимое. Явное удаление очищает файл и все его текстовые производные, отменяет задачи, оставляет только метаданные истории. Прежние дневники, анкеты и назначения не затрагиваются. Резервные копии удаляются владельцем сервера отдельно.
- Это политика нового локального исследовательского раздела. Для настоящей медицинской эксплуатации оператор, сроки/основания хранения, шифрование, регламенты и допуск остаются открытыми SEC-04/05 и E17; подтверждённая вспомогательная сводка сама не становится записью официальной меддокументации.

## Как получить краткий итог вместо прежнего длинного

В Terminal PyCharm из корня проекта, после остановки приложения и обработчика через Ctrl+C:

```powershell
git switch feat/local-mvp
git pull --ff-only origin feat/local-mvp
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

В отдельной вкладке Terminal того же проекта:

```powershell
.\.venv\Scripts\python.exe -m scripts.meeting_worker
```

Ollama должна оставаться запущенной. Откройте http://127.0.0.1:8000, войдите врачом. Панель «Пациенты / Календарь / Задачи / Библиотека / Настройки» теперь находится вверху и остаётся при прокрутке. Анкеты, лекарства и FAQ — в меню «Ещё».

Откройте пациента → профиль → консультации → записи встреч → нужную встречу. У уже расшифрованной записи нажмите «Подготовить итоги и следующие шаги». Видео заново загружать и расшифровывать не нужно. Старые итоги не сокращаются автоматически: создаётся новая версия с новым кратким текстом, прежние доступны в истории. Старая опубликованная версия доступна пациенту до отдельной публикации или отзыва врачом. Оригинал и полная расшифровка пациенту по-прежнему закрыты.

На короткой встрече нужен один запрос итогов. На длинной сначала готовятся опорные заметки, при необходимости несколько уровней объединения, затем общий итог; статус показывает эти этапы. По последнему уточнению пользователя нужен связный итог **6–7 предложений** о жалобах, важных темах и результатах встречи. Техническое ограничение — до 3 абзацев по 1000 символов, до 4 обсуждённых следующих шагов по 320 символов и до 3 приватных дополнений врачу по 320 символов, суммарно до 400 слов. Если исходник короткий, предложения ради количества не выдумываются. Раздел «Что можно дополнительно обсудить» видит только врач: это возможные вопросы/объяснения для следующего разговора, а не утверждение, что врач сделал ошибку. Ответственные и сроки добавляются только если они прозвучали; назначения/отмены лечения не создаются. Это ограничение автоматического черновика: врач по-прежнему может дополнять его в редакторе. Слишком длинный ответ модель сокращает одной новой попыткой; после повторного отказа показывается понятная ошибка, без сохранения частичного результата. Увеличение лимита ожидания не означает, что модель стала быстрее. Её скорость и качество на вашем компьютере проверяются отдельно.

При уменьшении COMPASS_SUMMARY_CHUNK_CHARS настройка задаёт размер исходных частей расшифровки. Уже короткие промежуточные заметки объединяются пакетами с порогом не менее 3000 символов, чтобы каждый следующий уровень уменьшал объём. Во время объединения общее число шагов может уточняться: это шаги подготовки итогов, а не минуты записи.


### После обновления формата до 6–7 предложений

Перезапустите и веб-приложение, и `scripts.meeting_worker`, чтобы они использовали одну версию настроек. У существующей записи снова нажмите «Подготовить итоги и следующие шаги»; оригинал и готовую расшифровку загружать заново не нужно. Это создаст новую версию, не перепишет предыдущую и не опубликует текст автоматически. Врач сверяет смысл и названия лекарств, редактирует текст, затем решает, что опубликовать. Новые вопросы анамнеза и голосовые заметки дневника хранятся отдельно от записей встреч.
