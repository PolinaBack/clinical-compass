Доработай существующий раздел «Авиандр — клиническая применимость» в ветке `feat/local-mvp` репозитория `PolinaBack/clinical-compass`.

Я хочу, чтобы экран перестал выглядеть как набор пустых серых полос. По каждому из четырёх направлений система должна ВСЕГДА показывать содержательный, индивидуальный и проверяемый вывод по данным выбранного синтетического пациента.

Важно: не придумывай медицинские факты, показания, противопоказания, взаимодействия или эффективность препарата ради заполнения интерфейса. Если данных недостаточно, делай содержательный вывод об ограничениях оценки, а не выдумывай положительный результат.

### 1. Изучи текущую реализацию

Проверь и переиспользуй:
- `app/routes/patient_ai.py`
- `app/templates/patient_ai.html`
- `app/templates/aviandr_analysis.html`
- `app/services/aviandr_analysis.py`
- `app/services/aviandr_sources.py`
- `app/services/patient_ai_data.py`
- существующие CSS, JS, сервисы Ollama и тесты.

Не переписывай рабочий механизм с нуля.

### 2. Четыре содержательные карточки

Для каждого направления показывай:

1. Название.
2. Статус.
3. **«Вывод по пациенту»** — 2–4 предложения.
4. **«На чём основан вывод»** — конкретные сведения из карты.
5. **«Что пока неизвестно»**.
6. **«Что уточнить врачу»** — 1–3 персонализированных вопроса.
7. Проверенный медицинский источник, если он есть.

Направления:

**Показания:** сопоставляй симптомы, диагнозы, результаты анкет и зарегистрированные показания. При отсутствии проверенной инструкции объясняй клинический контекст пациента, но не утверждай соответствие показаниям.

**Противопоказания:** анализируй документированные факторы и неполноту анамнеза. Если противопоказания не выявлены из-за недостатка данных, так и говори. Не приравнивай отсутствие записей к безопасности.

**Сочетаемость:** выводи фактический список текущих препаратов, проверенные взаимодействия и неизвестные сочетания. Если список неполный, указывай это явно.

**Переносимость:** если Авиандр не принимается, объясняй, почему оценка невозможна, и предлагай параметры наблюдения. Если есть подтверждённый приём, анализируй дневник, приверженность, нежелательные явления и изменения показателей без вывода о причинности.

### 3. Гарантированный вывод без Ollama

Реализуй для каждого направления функцию формирования содержательного текста на Python на основе фактов и статуса.

Она должна работать даже при выключенной Ollama.

Запрещены одинаковые универсальные тексты для всех пациентов, если их фактические данные различаются.

При отсутствии медицинских источников всё равно показывай факты пациента и конкретные ограничения оценки.

### 4. Улучшение с помощью Ollama

После детерминированного расчёта локальная Ollama должна:

- объяснять четыре направления естественным профессиональным языком;
- учитывать конкретные данные пациента;
- выделять противоречия;
- формировать индивидуальные уточняющие вопросы;
- ссылаться на идентификаторы исходных фактов.

Модель не должна менять рассчитанные статусы или добавлять новые неподтверждённые лекарственные свойства.

Если генерация не удалась, показывай полноценный Python-вывод, а не пустой экран.

### 5. Новый интерфейс

Замени текущие длинные серые полосы на сетку из четырёх карточек 2×2 для компьютера и одну колонку на телефоне.

В каждой карточке сразу должны быть видны:
- статус;
- короткий вывод;
- 2–3 основания;
- 1–2 вопроса;
- ссылка «Подробнее».

Под ними добавь:
- графики динамики симптомов;
- вопросы врачу;
- текстовое объяснение локального ИИ;
- информацию об источниках и ограничениях.

Цвета используй в соответствии с существующим дизайном «Компаса». Не делай числовую шкалу полезности или безопасности.

### 6. Обновление данных

При изменении анамнеза, текущих препаратов, анкет, дневника или сведений о приёме расчёт должен обновляться.

Показывай дату анализа и предупреждение, если текст Ollama устарел относительно текущих данных.

### 7. Проверка на трёх синтетических пациентах

Проверь:
- пациент с тревожной симптоматикой, у которого препарат только рассматривается;
- пациент с несколькими лекарствами и неполными сведениями;
- пациент с подтверждённым учебным приёмом, пропусками и возможным нежелательным явлением.

У всех трёх должны отображаться четыре содержательные карточки, но с разными выводами, соответствующими их данным.

Если синтетические сценарии уже есть, используй их, не создавая дубликаты.

### 8. Тесты

Добавь тесты на:
- содержательный вывод для каждого направления;
- работу без Ollama;
- корректность при отсутствии официальной инструкции;
- отсутствие выдуманных взаимодействий;
- отсутствие ложного утверждения о безопасности;
- изменение вывода при обновлении данных;
- разграничение доступа врачей;
- отсутствие автоматического назначения или изменения терапии.

### 9. Результат

Внеси реальные изменения в код.

После завершения:
- перечисли изменённые файлы;
- покажи, как открыть новый экран;
- приведи четыре фактических вывода для каждого демонстрационного пациента;
- укажи, что работает без Ollama, а что требует Ollama;
- сообщи результаты запущенных тестов;
- не утверждай, что модуль клинически валидирован.

Цель: создать красивый, информативный и действительно персонализированный исследовательский экран, который помогает врачу разбираться в применимости Авиандра, не выдавая предположения за доказанные медицинские факты.
