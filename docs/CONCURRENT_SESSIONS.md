# Одновременная работа в одном аккаунте

25.10.2026 · U-CONCURRENT-SESSIONS-25.

Несколько устройств или независимых браузеров могут одновременно входить под одним логином врача либо пациента, переходить между доступными разделами и сохранять данные. У каждого браузера свой cookie и CSRF-токен. Второй вход и выход другого браузера не отзывают ваш сеанс.

Ранее каждый `create_app` создавал случайный ключ подписи cookie. Другой серверный процесс и перезапуск не распознавали вход; отправленная из открытой формы операция, в том числе выход, могла завершиться 403 из-за потерянного CSRF-токена. Теперь все процессы одной базы используют постоянный приватный ключ. Повторное нажатие «Выйти» из уже закрытого сеанса возвращает на начальную страницу без ошибки.

## Обновить в PyCharm

Остановите сервер, выполните в терминале корня `clinical-compass`:

```powershell
git switch feat/local-mvp
git pull --ff-only origin feat/local-mvp
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

После первого обновления войдите заново: прежний случайный ключ не сохранялся. Затем обычные перезапуски сохраняют действующий вход. Пароли, пациенты, заполнения и назначения это исправление не меняет; команды сброса/создания БД не нужны. Новых зависимостей и миграций нет.

## Проверить вручную

1. Откройте сайт в двух разных браузерах либо в обычном и приватном окне. Два обычных окна одного профиля разделяют cookies и не являются независимыми сеансами.
2. В обоих войдите под одним логином специалиста. В первом откройте дневник закреплённого пациента и форму комментария, во втором перейдите в календарь, библиотеку, форумы и настройки.
3. Сохраните комментарии из обоих браузеров. Оба должны появиться после обновления. Выход во втором не должен мешать первому открыть раздел и сохранить ещё один комментарий.
4. До выхода оставьте во втором браузере дополнительную вкладку с кнопкой выхода. После выхода нажмите эту кнопку из оставленной вкладки: откроется главная страница без 403.
5. Повторите с одним пациентским логином: откройте дневник и сохраните разные заметки из обоих браузеров. После выхода одного второй продолжает работать.
6. Оставьте открытую форму. Остановите и снова запустите сервер с тем же `COMPASS_DB` и тем же ключом; отправьте форму без повторного входа. Действующий CSRF-токен продолжает работать.

Право доступа проверяется для каждого запроса. Обращение к чужой карте и подставленный CSRF-токен по-прежнему запрещаются. Одновременное изменение одной версии анкеты/черновика может привести к предусмотренному конфликту 409 — нужно перечитать последнюю версию, чтобы не затереть чужие изменения. Смена пароля или отключение аккаунта отзывает все его сеансы. Срок cookie по-прежнему ограничен восемью часами, обновляемыми при работе.

## Как хранится ключ

По умолчанию рядом с выбранной базой создаётся `<полный путь базы>.session.key`, например `data/compass.db.session.key`. Путь привязан к базе, а не к текущему процессу. Ключ не содержит медицинских данных; он нужен для проверки подписи сеансов и отличается от ключа шифрования вложений. Не удаляйте его при обычном обновлении и не добавляйте в Git. Для нового файла используются приватные права; на Windows доступ дополнительно определяется ACL каталога пользователя.

При параллельном первом старте каждый процесс подготавливает законченный временный файл, затем публикует один победивший ключ без перезаписи. Незавершённый ключ не читается другим процессом. Изменённый/некорректный существующий файл не заменяется молча: приложение сообщает об ошибке настройки.

Для нескольких экземпляров приложения можно задать **одинаковый** `COMPASS_SESSION_KEY_FILE` с общим приватным файлом либо **одинаковый** `COMPASS_SESSION_SECRET` со случайным секретом длиной от 32 символов. Явный секрет имеет приоритет над файлом; не задавайте разные значения разным процессам. Для отдельных независимых установок используйте разные секреты. Значения секретов не помещайте в код, команды в общей истории или журнал. Обычная локальная установка не требует этих переменных.

Атомарная публикация использует жёсткую ссылку, поддерживаемую локальными NTFS/Linux-файловыми системами. Если сетевой/виртуальный диск её не поддерживает, приложение сообщает об этом; используйте согласованный секрет окружения или подходящий каталог ключа. Случайного запасного ключа на процесс нет.

Копия SQLite сохраняет данные без этого ключа: при восстановлении с новым ключом пользователи входят заново. Ключ шифрования данных по-прежнему сохраняется существующим скриптом резервного копирования отдельно и обязателен для зашифрованных записей.

## Техническая проверка

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_concurrent_sessions.py
.\.venv\Scripts\python.exe -m pytest -q
```

Проверены отдельные сеансы врача и пациента, настоящие параллельные записи, несколько экземпляров приложения и перезапуск, независимый/повторный выход, сохранённые защиты, параллельное создание ключа и ошибочная конфигурация. Chromium дополнительно проверен через два настоящих HTTP-процесса и четыре независимых контекста браузера, с двумя настоящими перезапусками. Использовалась временная синтетическая база. Linux/Chromium проверены; Windows/PyCharm вручную не запускались.
