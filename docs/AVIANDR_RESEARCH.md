## Обновление и чистая демобаза в PyCharm

Остановите приложение и все ИИ/аудио-обработчики. Откройте терминал в корне `clinical-compass`:

```powershell
git switch feat/local-mvp
git pull --ff-only origin feat/local-mvp
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m scripts.setup_aviandr_scenarios --reset
```

**`--reset` выполняет согласованную очистку:** старая база целиком сохраняется в `data/backups/before-aviandr-reset-….db`, её ключ — рядом при наличии зашифрованных записей. Затем база заменяется подготовленной и проверенной новой SQLite с тремя пациентами и двумя специалистами. Старые заполнения, встречи, назначения, сообщения и прочие записи прежней базы не переносятся в новую; они остаются в резервной копии. Это явная команда, автоматической очистки при запуске сайта нет.

Сохраняются пароли первых двух активных врачебных и первых трёх активных пациентских аккаунтов. При обычном прежнем наборе это существующий специалист и оба пациента; их логины и пароли останутся прежними. Пациентские аккаунты привязываются к новым C/D/E по порядку. Недостающие аккаунты создаются со случайными паролями, которые скрипт покажет только при создании. Сохраните их в личном менеджере. Остальные прежние аккаунты, если они были, остаются в полной резервной копии.

Старые сеансы входа отзываются для **всех** новых аккаунтов, включая созданные при очистке: совпадение номера записи не даёт старой пациентской сессии доступ к новому специалисту. Войдите снова обычным способом; сохранённые основные пароли менять не требуется.

По умолчанию используется `data/compass.db` либо `COMPASS_DB`. Для конкретного файла:

```powershell
.\.venv\Scripts\python.exe -m scripts.setup_aviandr_scenarios --db .\data\compass.db --reset
```

Приложение и worker должны использовать этот же файл. При другом `COMPASS_ATTACHMENT_KEY_FILE` сохраните прежнюю настройку ключа. Сброс блокируется, если обнаружен активный WAL или исходная база изменилась во время подготовки. Резервная копия не перезаписывается.

### Если Windows сообщает WinError 5 или файл занят

Ошибка на `os.replace(...fresh.db, ...compass.db)` означает, что ОС отказала в последней замене файла. Копия прежней базы создаётся до этого шага. Не удаляйте `compass.db`, файлы ключей или папку `backups` вручную.

1. Нажмите **Stop** во всех Run/Debug-конфигурациях PyCharm: сервер, ИИ и аудио-обработчики. В терминалах с ними — Ctrl+C.
2. Закройте вкладки просмотра `compass.db`. Если подключали базу в панели **Database**, нажмите по соединению правой кнопкой → **Disconnect**. Закройте DB Browser for SQLite и другие программы, открывшие этот файл.
3. Обновите код через `git pull --ff-only origin feat/local-mvp`, затем повторите команду сброса в терминале. Для неё не нужен запущенный сервер.

Скрипт кратко повторяет атомарную замену при временной блокировке. Атрибут «только чтение» самого файла на Windows снимается для согласованного сброса; при неудаче он восстанавливается на исходном файле. Перед каждой попыткой снова проверяются содержимое базы и WAL: новая запись во время ожидания отменяет замену. При постоянной блокировке выводятся понятное сообщение и точный путь к резервной копии, без traceback и без сообщения об успешном сбросе. Скрипт не удаляет занятую базу перед заменой, не отключает антивирус и не меняет права всей папки.

Если после Disconnect ошибка остаётся, закройте PyCharm, откройте обычный PowerShell в папке проекта и выполните ту же команду при остановленных сервере и обработчиках. Если файл всё ещё заблокирован или доступ запрещён политикой Windows, сброс остановится с сохранением копии; принудительная перезапись не выполняется.

Повторная подготовка **без очистки**:

```powershell
.\.venv\Scripts\python.exe -m scripts.setup_aviandr_scenarios
```

Она добавляет только отсутствующие сценарии; не дублирует пациентов/дневники и не перезаписывает ручные изменения. Уже созданный 30-дневный сценарий остаётся привязан к исходной дате. Не используйте `--reset` при каждом запуске.

## Запуск приложения и настоящей локальной модели

Первый терминал PyCharm:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Для текстового ИИ нужна установленная локальная Ollama. Во втором терминале, если сервис ещё не запущен:

```powershell
ollama serve
```

В отдельном терминале один раз загрузите предобученную модель и проверьте её наличие:

```powershell
ollama pull qwen2.5:3b
ollama list
```

Запустите обработчик очереди в ещё одном терминале корня проекта:

```powershell
.\.venv\Scripts\python.exe -m scripts.patient_ai_worker
```

Он обрабатывает прежние общие сводки и новые объяснения Авиандра. Обновлённый `scripts.experimental_ai_worker` также поддерживает новые задания. Это альтернативные способы запуска; одновременно запускать оба не нужно.

По умолчанию Ollama вызывается по `http://127.0.0.1:11434`; модель — `qwen2.5:3b`, тайм-аут — 600 секунд. Настройки `COMPASS_EXPERIMENT_OLLAMA_URL`, `COMPASS_EXPERIMENT_OLLAMA_MODEL`, `COMPASS_EXPERIMENT_TIMEOUT` должны совпадать в терминале обработчика с вашими локальными настройками. Разрешён только loopback HTTP, без облачных моделей и перенаправлений. На медленном компьютере можно увеличить тайм-аут до 1800 секунд. Контекст нового объяснения — 16384 токена; модель и память компьютера должны это поддерживать.

Откройте `http://127.0.0.1:8000`, обновите страницу Ctrl+F5. Для двух специалистов и пациента используйте разные профили браузера/приватное окно. Первый специалист видит C/D, второй — E. Если аккаунты создавались впервые, второй обычно называется `specialist-2`; реальные новые логины и пароли выводит скрипт.

В разделе Авиандра нажмите **Объяснить этот расчёт с помощью ИИ**, затем **Обновить объяснение** после завершения. Кнопка обновления выполняет обычный GET формы, а не переход к тому же фрагменту страницы: результат действительно перечитывается с сервера. Проверяемые статусы, вопросы по пробелам и исходные данные доступны до запуска модели и при её ошибке.

## Четыре направления и источники

Python-код читает отправленную версию анамнеза, врачебные уточнения, полную сохранённую историю анкет с ответами, дневник, фактические отметки, сообщения о реакциях и последние отправленные пожелания пациента. Частные черновики анамнеза и лекарственные черновики не становятся текущей терапией. Отправленная схема документирует назначение; фактический приём требует отдельного сведения/отметки. Неизвестное лекарство или несовпадающее МНН не получают подтверждённую идентификацию автоматически.

- **Показания:** положительный статус требует подтверждённой записи диагноза и действующего проверенного правила. Жалобы и скрининговые баллы остаются данными для динамики и вопросов.
- **Противопоказания:** отдельно учитываются подтверждённые и сообщённые факторы, неизвестные значения и отсутствие совпадения. Противоречащие подтверждённые записи требуют уточнения. Отсутствие совпадения не означает отсутствия противопоказаний.
- **Сочетаемость:** проверяются конкретные пары с подтверждённой идентификацией текущей терапии и активными верифицированными записями библиотеки. Указываются объяснение, источник, дата, РУ, форма и раздел. Редакционная матрица не считается подтверждённым взаимодействием; отсутствие пары не подтверждает безопасность.
- **Переносимость:** фактический статус/дата начала, отдельные отметки и причины пропусков, симптомы, пожелания и изменения записанных значений до/после. Дни до начала и дни без записи не считаются пропусками приёма. Сообщение пациента и отдельная врачебная оценка связи сохраняют своё происхождение.

У каждой карточки есть раскрытие и предварительные сведения именно выбранной карты: возраст, последние суммы, текущие лекарства или фактические отметки. Диаграмма показывает четыре независимых статуса без общего процента пригодности. Цвет не является рекомендацией препарата.

### Предоставленный фрагмент ГРЛС

В модуле сохранены присланные регистрационные сведения: **ЛП-№(002445)-(РГ-RU)**, ООО «Авинейро», 31.05.2023–31.05.2028, химическое наименование и прочие указанные поля. Производитель не дописан: исходная строка обрывается. Состояние «ИЗМ» сохранено без придуманной расшифровки.

Это регистрационный фрагмент. Он не содержит разделов показаний, противопоказаний, взаимодействий и нежелательных реакций и **не создаёт клинических правил**. Прямой ссылки на полную актуальную инструкцию в фрагменте нет. В среде разработки онлайн-сверка ГРЛС не состоялась; подлинность и актуальность полного документа автоматически не заявляются. Поэтому в исходных C/D/E соответствующие статусы остаются неопределёнными. Это предусмотренное поведение, а не приготовленный «благоприятный» результат.

### Как подключить проверенную инструкцию

1. В **Библиотека → Лекарства → Импорт** загрузите полный официальный PDF или XLSX по существующему шаблону. Укажите прямую HTTPS-ссылку на конкретную запись/документ ГРЛС, точный РУ, форму, редакцию, дату сверки и срок следующей проверки. Заполните только действительно сверенные фрагменты с разделом/страницей.
2. Подтвердите импорт и отдельно выполните существующую врачебную проверку источника. Сам импорт или редакционная карточка не подтверждает документ.
3. В **Анализ ИИ → Проверенные источники и правила** появится форма для операционализации проверенной цитаты. Для Авиандра учитываются активные источники D01 с указанным РУ. Выберите вид правила, факт, точный код/обозначение и условие. Для показаний используется диагноз; для нежелательного проявления — точный медицинский термин реакции; числовые условия предусмотрены для возраста.
4. Дословная цитата должна входить в соответствующий проверенный раздел источника. Перед сохранением доступна видимая отметка сверки условия и цитаты. Сервер проверяет типы, раздел, цитату, хеш и активность источника. **Смысл соответствия условия цитате проверяет врач**, он не устанавливается автоматически моделью.
5. Конкретные взаимодействия берутся из ранее поддержанного структурированного листа «Взаимодействия» проверенного импорта. Свободный текст PDF автоматически не превращается в правила пар. Без такой записи оценка остаётся ограниченной.
6. При отзыве, замене или истечении срока источника новый расчёт перестаёт использовать его правила. Прежний снимок объяснения остаётся историческим и не показывается как актуальный.

Не переносите технические фикстуры из тестов в реальную библиотеку как медицинские сведения. В поставленной базе нет искусственно «подтверждённых» противопоказаний или взаимодействий. Выбор эффектов пациентом использует редакционный словарь названий; сам этот выбор не верифицирует лекарственное свойство в новом разделе.

## Ручная проверка

1. **C:** откройте четыре карточки, нажмите также на диаграмму. Проверьте неизвестную переносимость, источник анкет, исходные ответы и 3–7 вопросов по фактическим пробелам.
2. **D:** раскройте сочетаемость. Должен быть виден D11 с неподтверждённой идентификацией. Не должно быть вывода о безопасной совместимости или произвольного взаимодействия из матрицы.
3. **E:** войдите вторым специалистом, раскройте переносимость. Проверьте дату начала, 14 отмеченных дней/2 пропуска, отсутствие ложных пропусков за 14 предшествующих дней, причины, тошноту и разделение сообщения/оценки врача. Показаны отправленные пожелания пациента и главный эффект.
4. **Пациент E:** в **Профиль → Мои назначения и обследования → Лекарства**, внутри отправленного препарата откройте **Отметить фактический приём за день**. Выберите «Не могу уточнить» за последний день, сохраните. У врача после обновления должны стать 13 отмеченных дней/2 пропуска/1 неизвестный, а не второй дубликат дня.
5. Сообщите о проявлении из прежней формы реакции. У врача оно появляется с происхождением, датой и отдельной оценкой связи; препарат и схема не меняются.
6. Измените отправленные пожелания либо заполните новую анкету/дневник. Обновите расчёт: сведения меняются, неполное не превращается в ноль. Старое объяснение отмечается устаревшим; новый текст требует нового запуска.
7. В **Добавить уточнённое сведение врача** сохраните возраст/фактор/идентификацию с основанием. Дата и проверка находятся в той же раскрывающейся форме. Повтор той же отправки идемпотентен; изменение данных старым токеном не выдаётся за новое успешное сохранение.
8. Нажмите **Объяснить этот расчёт с помощью ИИ** при работающих Ollama и worker. После завершения обновите объяснение: ожидаются сводка, четыре пояснения, 3–7 вопросов и при наличии противоречия, с привязкой к допустимым основаниям.
9. Остановите Ollama и повторите запуск. Должна быть явная ошибка соединения/модели/тайм-аута; расчёт и вопросы Python остаются, готовый ответ модели не подставляется. Если worker не запущен, задание честно остаётся в очереди.
10. Попробуйте открыть E первым специалистом или ИИ-вкладку из пациентского аккаунта: сервер запрещает доступ. Без JavaScript доступны текущий расчёт, раскрытия и обычные формы; для завершившегося задания можно обновить страницу.
11. Повторите подготовку без `--reset`: число пациентов/дневников не растёт, ручные изменения остаются. Проверяйте очистку повторно только на копии или при намерении снова вернуть сценарии к исходному состоянию.

## Технические проверки и ограничения

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_aviandr_research.py tests/test_patient_ai.py
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты создают временные синтетические базы. Проверены расчёты, источники/отзыв/цитаты, роли/CSRF/версии, ошибки транспорта, структура ответа/ссылки, неизменность статусов моделью, сохранение паролей и защита от старых сеансов при очистке. Тестовые медицинские фрагменты намеренно подписаны как фикстуры и не включаются в пользовательскую базу.

В этой среде Ollama не установлена и не запущена: проверен настоящий неуспешный HTTP-вызов loopback из worker, без mock-сервера, и отсутствие поддельного результата. Успешные структурированные ответы проверены через явно помеченный тестовый HTTP-транспорт. **Успешная генерация именно вашей локальной моделью требует ручной проверки после запуска в PyCharm.** Положительный результат тестов не доказывает клиническую достоверность.

Языковая модель предобучена, но не проходила специального медицинского дообучения/клинической валидации в этом проекте. Она объясняет переданный снимок; статусы и медицинские правила не редактирует. Сервер проверяет структуру и допустимые основания, отсекает ряд назначений/процентов/причинных утверждений; это не доказательство смысловой правильности свободного пересказа. Текст проверяет врач. Модель не получает все оригинальные документы: передаются рассчитанные основания, актуальные формы по инструментам и ограниченный контекст записей; покрытие фиксируется в provenance. Слишком большой контекст отклоняется без фиктивного ответа.

Нет автоматического подбора препарата/дозы, изменения лечения, прогноза переносимости в процентах, клинической валидации, гарантии безопасности, автоматического онлайн-импорта ГРЛС или регистрации медицинского изделия. Частные черновики, несвязанные общие отметки приверженности, содержимое нерасшифрованного аудио/видео и PDF не выдаются за подтверждённые факты. Windows/PyCharm вручную в среде разработки не запускались.

Для будущей экспертной оценки предусмотрены стабильные ID запусков/оснований, версии алгоритма/промпта/сценария, зашифрованные снимки с хешами и источниками, неизменяемые наблюдения/правила. Экспертные оценки можно связывать с `aviandr_runs.id` отдельной таблицей, не переписывая расчёт и транспорт. Клиническая проверка значений предикатов, источников, переводов шкал и качества вопросов остаётся отдельной работой.
